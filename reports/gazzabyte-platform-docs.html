PART 02

Tabung approval workflow

How a weekly tabung (collection) report moves from a working draft to a closed, dual-signed record — and the safeguards that make sure no single person can quietly complete it.

DRAFT
Figures are entered here; the report stays editable while it remains a draft.
Preparer signs
PREPARER_SIGNED
Locked from edits. The preparer's signature is recorded in a tamper-evident audit trail.
Endorser closes
(must differ)
CLOSED
Finalised. Signed by a preparer and endorsed by a second person.
↺ REOPEN
Only an org admin can send a preparer_signed report back to draft, and only with a recorded reason. A report that has ever been signed keeps that mark permanently — reopening cannot clear it — and that is what enforces preparer-only re-signing (below). A closed report is terminal: it cannot be reopened.
Dual control

Two people, always

The person who endorses a report to close it must not be the same person who signed it. Preparing and endorsing are structurally separated — enforced by the system, not by policy alone.

Safeguard

Preparer-only re-signing

Once a report has been signed and then sent back, only the preparer can sign it again — an administrator can't step in and take that action while an active preparer exists. An admin fallback applies only when no preparer is assigned, and it is recorded when it does.

Safeguard

Tamper-evident trail

Each signing writes a link in a hash-chained audit record. Any later alteration to the sequence is detectable — the trail can't be quietly rewritten.

Coming next release

Correct a banked amount before signing

An upcoming release lets a preparer correct a banked tin's counted amount while the report is still a draft — with a required reason, the amount and its breakdown written in one all-or-nothing step, and old → new appended to the audit trail. It freezes the moment the report is signed. Rolling out shortly.

Reading this
“Preparer” and “endorser” are roles, not fixed people — an institution assigns them. The guarantee is about separation: the platform will not let one person both sign and endorse the same report.
PART 03

Access & usage

Who can see and do what, and the standard procedures for setting it up — both the reseller controls you hold and the in-institution controls their administrator holds.

The two-key access model

Every module a person can reach passes through two independent gates. Turning a module on for an institution does not, by itself, show it to anyone — a role still has to be given access. Both keys must turn.

Key 1 · You (Gazzabyte)

Module enablement

From the administration layer you switch a module on or off for a whole institution. This is the reseller decision — what that institution has purchased or is entitled to.

×

Key 2 · Their admin

Role permission

Inside the institution, their administrator grants each role access to an enabled module — full access or none. This is the customer's own internal decision.

A module is visible to a user only when it is enabled for the institution and opened to that user's role. Either key left unturned keeps it hidden.

SOP A — Reseller: turn a module on for an institution

Open the administration layer and find the institution in the organisation directory.
In its module control, switch the required module on (or off). This sets what the institution is entitled to — it does not yet expose it to any user.
Tell the institution's administrator it's available so they can complete Key 2 (SOP C).

SOP B — Reseller: grant platform-administrator access

Confirm the person should hold reseller-level access — platform administration spans the control layer, so grant it deliberately and to as few people as the job needs.
Add them as a platform administrator from the administration layer.
Verify they appear in the platform-administrator list and can reach the control layer.

SOP C — Institution admin: open a module to a role

Sign in as the institution's org admin (the module must already be enabled by the reseller — Key 1).
In role permissions, set the relevant role to full access for that module (or none to withhold it).
Users in that role now see the module on their dashboard. For tabung, assign preparer and endorser to different people so dual control holds.
Least privilege
Both key-holders should grant the narrowest access that does the job — enable only the modules an institution needs, and open each module only to the roles that use it. It's easier to widen access later than to walk back an over-broad grant.
