# Wingmen Orchestrator — Substrate Audit Report

## A. Executive Summary

The substrate's governance logic is sound but its **data-layer authorization is systemically broken**: RLS is either misconfigured with `USING(true)` "service-role" policies that never test `auth.role()` (26 tables) or disabled outright (23 tables), while Supabase's default `anon`/`authenticated` DML grants sit on top — the net effect is that **anyone holding the project anon key can read, write, and delete client PII, payment schema, the operator's private Telegram log, and every control-plane table** over PostgREST. This is severe but currently **latent**: no anon key for this project ships in the repo or frontend (the console uses a server-side service-key backend), so exploitation is gated on non-distribution of the anon key — the moment any frontend/edge function ships it, the whole set becomes a P0 internet-wide breach. On top of the authz gap, three independent message-durability defects (offset-before-log ordering, channel-blind reconciliation cursor, unretried getFile hop) each defeat the exact Option-B "durable log is the source of truth" guarantee for operator/partner/paid-client messages.

**Posture:** authz = broken-but-gated (fix before any anon key ships); durability = actively leaking messages under fault/interleave; view-integrity + hygiene = latent, already policy-guarded. **Prioritized fix queue in section C.**

### B1. Authorization / RLS / Grants (P1)

#### [P1] Misconfigured "service role" policy leaves 26 RLS-enabled tables wide open to anon
**Object:** `public.jobs, clients, work_outputs, payments, bug_reports, build_log, repo_memory, chat_history, usage_log, pending_signups, message_queue, wingmen_brain, bot_users, bot_conversations, provisions, fleet_lanes, jobs_archive, strategic_decisions_archive, bot_heartbeat, brain_sync_log, cc_work_sessions, client_repos, drift_audits, ecosystem_audit_log, repo_snapshot, site_templates` (26 tables)
**Location:** `pg_policies` — sole policy `service role full access` / `wingmen_brain_service`
**Verdict:** CONFIRMED (independently reproduced against live substrate)

The single PERMISSIVE `FOR ALL TO public USING(true) WITH CHECK(true)` policy never tests `auth.role()`. RLS being ON masks this from a casual audit. `has_table_privilege('anon', ...)` confirms anon holds SELECT/INSERT/UPDATE/DELETE on all 26. `clients` has 8 real rows with email/telegram_username/stripe_customer_id (PII — note this contradicts the "Sydney/no-PII substrate" assumption in memory); `work_outputs` has 232 audit rows; `payments` schema holds `amount_cents`/`provider_charge_id`/`plan`.

**Impact:** Exfiltrate client/payment PII, forge/delete jobs, tamper audit trails (`ecosystem_audit_log`, `drift_audits`), deface `site_templates`, take over control-plane (`message_queue`, `fleet_lanes`, `provisions`) — for any anon-key holder.

**Fix** (direct psycopg dry-run→apply, never `supabase db push`):
```sql
-- per table, replace the fake policy with a real role gate
DROP POLICY "service role full access" ON public.jobs;
CREATE POLICY svc_all ON public.jobs FOR ALL TO public
  USING (auth.role() = 'service_role')
  WITH CHECK (auth.role() = 'service_role');
-- defense in depth: grant is independent of RLS
REVOKE ALL ON public.jobs FROM anon, authenticated;
-- assert
SELECT has_table_privilege('anon','public.jobs','INSERT');  -- expect f
```
Repeat for all 26 (`wingmen_brain` uses policy name `wingmen_brain_service`).

#### [P1] operator_messages — private operator conversation, RLS off + anon DML (the crown-jewel PII table)
**Object:** `public.operator_messages` (migration `007_operator_messages.sql`)
**Location:** written at `tg_bridge.py:399`, `operator_log.py:24`
**Verdict:** CONFIRMED (write surface actually *understated* — anon also holds DELETE + TRUNCATE)

Holds the full operator↔orchestrator private Telegram conversation plus Desmond/Shen partner + irsyad-support client text (1788 rows live). `relrowsecurity=false`, zero rows in `pg_policies`, anon holds SELECT/INSERT/UPDATE/**DELETE/TRUNCATE**. It is the **only** bridge table without a `service_role` RLS fence — contrast `agent_messages` (RLS on + service-role policy → anon SELECT returns 0 rows).

REVOKE INSERT, UPDATE, DELETE, TRUNCATE ON public.operator_messages FROM anon, authenticated;
-- keep console_readonly SELECT (existing grant); verify:
SELECT has_table_privilege('anon','public.operator_messages','DELETE');  -- expect f
```

#### [P1] Governance/PII base tables readable + spam-writable by anon via `USING(true)` policies
**Object:** `strategic_decisions, session_digests, repo_context` (anon SELECT); `pos_orders, pos_order_items, ui_events` (anon INSERT)
**Location:** `pg_policies` — `decisions_read_all`/`digests_read_all`/`repo_context_read_all` (SELECT `USING true` TO public); `'Anyone can place orders'`/`'Anyone can insert order items'`/`anyone_can_insert_events` (INSERT `CHECK true` TO public)
**Verdict:** CONFIRMED

Governance memory is anon-readable: `strategic_decisions`=712 rows (decision/reasoning/quranic_basis/source_chat_url), `session_digests`=542, `repo_context`=8 (architecture/known_debt/blockers). **Fix:**

DROP POLICY digests_read_all ON public.session_digests;
DROP POLICY repo_context_read_all ON public.repo_context;

DROP POLICY "Anyone can place orders" ON public.pos_orders;
CREATE POLICY orders_insert ON public.pos_orders FOR INSERT TO authenticated
  WITH CHECK (org_id = ANY (auth_user_org_ids()));
-- ui_events: scope to authenticated (+ app-side rate limit)
DROP POLICY anyone_can_insert_events ON public.ui_events;
CREATE POLICY events_insert ON public.ui_events FOR INSERT TO authenticated WITH CHECK (true);
```
(Note: dropping the governance read policies is safe because `boot_briefing`'s security-invoker fix below routes fleet reads through service_role, not anon.)

#### [P1] Seven SECURITY DEFINER functions anon-callable with no pinned search_path
**Object:** `auth_user_org_ids(), auth_user_org_ids_with_role(text), auth_user_org_ids_with_roles(text[]), auth_user_hr_employee_id(), handle_new_user(), sync_org_memberships_to_jwt(), enforce_agent_status_identity()`
**Location:** `pg_proc`: `prosecdef=true`, `proconfig=NULL`, anon+authenticated EXECUTE=true
**Verdict:** CONFIRMED (RLS dependency **understated** — 124 policies across 48 tables, not 85)

All seven run as owner `postgres` with caller-controlled `search_path`. anon AND authenticated both hold TEMP on the DB (`has_database_privilege TEMP=true`), so they can create `pg_temp` objects; PG searches `pg_temp` first for relation resolution. `auth_user_hr_employee_id()` references **unqualified** `hr_employees`/`persons`, and `enforce_agent_status_identity()` calls unqualified `log_agent_status_identity_violation()` — concretely temp-shadowable, executing under postgres rights. The `auth_user_*` set is the tenant-isolation primitive underpinning 124 RLS policies. (Correction to the finding: `auth_user_org_ids()`/`sync_org_memberships_to_jwt()`/`handle_new_user()` *do* schema-qualify their refs — the shadow vector lands via the hr/persons/violation-log helpers, but the unpinned-SECDEF + anon-EXECUTE hardening hole spans all seven.)

ALTER FUNCTION public.auth_user_org_ids_with_role(text) SET search_path = public, pg_temp;
ALTER FUNCTION public.auth_user_org_ids_with_roles(text[]) SET search_path = public, pg_temp;
ALTER FUNCTION public.auth_user_hr_employee_id() SET search_path = public, pg_temp;
ALTER FUNCTION public.handle_new_user() SET search_path = public, pg_temp;
ALTER FUNCTION public.sync_org_memberships_to_jwt() SET search_path = public, pg_temp;
ALTER FUNCTION public.enforce_agent_status_identity() SET search_path = public, pg_temp;
-- these are trigger/RLS-internal, not client API surface:
REVOKE EXECUTE ON FUNCTION
  public.auth_user_org_ids(), public.auth_user_org_ids_with_role(text),

#### [P1] SSRF / arbitrary-dynamic-SQL primitive callable by anon
**Object:** `public.fetch_and_execute_sql(text)`, `public.load_all_morphology_batches(text,integer,integer)`
**Location:** `pg_proc`: `prosecdef=false`, anon+authenticated EXECUTE=true
**Verdict:** CONFIRMED (severity raised P2→P1: blast radius larger than "runs as unprivileged invoker" implies)

`fetch_and_execute_sql` does `http_get(url)` then `EXECUTE <fetched body>` — remote-fetch-then-dynamic-SQL. `http` extension is in `public`, `http_get` is itself anon-executable, and anon has schema USAGE → RPC-callable via `POST /rpc/fetch_and_execute_sql`. Because the dynamic EXECUTE runs **as anon**, and anon holds INSERT/UPDATE/DELETE on the 23 RLS-off control-plane tables above, an attacker-hosted SQL payload can freely poison `identity_allowlist`/`operator_messages`/runtime config. Plus a raw SSRF surface: `http_get` takes an arbitrary URL with no internal-IP/metadata blocklist, from the DB host's network position.

**Fix:**
```sql
REVOKE EXECUTE ON FUNCTION public.fetch_and_execute_sql(text)
  FROM anon, authenticated, PUBLIC;
REVOKE EXECUTE ON FUNCTION public.load_all_morphology_batches(text,integer,integer)
  FROM anon, authenticated, PUBLIC;
-- if internal-only, leave service_role; verify:
SELECT has_function_privilege('anon','public.fetch_and_execute_sql(text)','EXECUTE'); -- expect f
```
(Note: fixing the 23 RLS-off tables and the anon `http_get` grant both independently shrink this blast radius — do all three.)

### B2. Message Durability / Reconciliation (P1)

#### [P1] Telegram offset persisted BEFORE inbound is logged — crash loses the message
**Object:** `nervous_system/tg_bridge.py` (mirrored: `cai_bridge.py`, `irsyad_support_bridge.py`)
**Location:** `tg_bridge.py:461` (offset write) vs `:399` (inbound log)
**Verdict:** CONFIRMED

`main()` writes the advanced offset to disk (`:461 OFFSET_FILE.write_text`) **before** `handle()` (`:466`) reaches the durable `operator_log.log("inbound", ...)` at `:399`. Once the offset advances, `getUpdates(offset)` ACKs that `update_id` to Telegram permanently (no raw-update journal/WAL — only the single offset file). The loop body is wrapped in `try/except Exception` (`:467`), so an exception before `:399` — most concretely the **unguarded `operator_log.log()` psycopg.connect** raising on a transient network/DB fault (the codebase's own Errno-54 flakiness) — or process death (launchd restart / OOM / deploy) in that window loses the message from Telegram *and* the log, invisible to `unprocessed()`. Defeats CAI-RESP-277's core guarantee. (The media-download sub-path is actually guarded and still reaches `:399`; the real triggers are the DB-connect raise and process death.)

**Fix — log-then-ack.** Persist the offset only after `operator_log.log()` commits:
```python
authorize(m)
handle(m, chat, sender)      # includes the durable operator_log.log() at :399
offset = u["update_id"] + 1  # only NOW advance
OFFSET_FILE.write_text(str(offset))
```
A crash before the offset write re-delivers the update on next boot; reconciliation dedups the already-written row → at-least-once restored. Apply identically in `cai_bridge.py` and `irsyad_support_bridge.py`.

#### [P1] Reconciliation cursor is channel-blind — answering one channel silently marks others handled
**Object:** `nervous_system/operator_log.py`
**Location:** `unprocessed()` (`:57-60`), `mark_handled_through()` (`:71-74`)
**Verdict:** CONFIRMED (vulnerable interleaved state present in prod at verification time)

Both filter only `direction='inbound' AND handled_at IS NULL` (`mark_handled_through` also `id <= max_id`) with **no tag/channel predicate**, while three bridges multiplex distinct channels into one table with monotonic ids: `tg_bridge.py:399` (DM), `cai_bridge.py:353` (`cai-channel`), `irsyad_support_bridge.py:248` (`gazzabyte-irsyad`). Live at verification: unhandled backlog was `cai-channel {1768,1773,1780}` interleaved with DM `{1769..1789}`. If cc-orch answers the DM traffic and calls `mark_handled_through(1789)`, the three unanswered war-room rows get `handled_at=now()` and **never resurface** — silent partner/paid-client message loss. Aggravated by (1) the war-room protocol where cc-orch legitimately does *not* answer many `cai-channel` rows yet stamps them, and (2) shared-core cross-brain race where cai reconciles the same untagged cursor.

**Fix — scope the cursor by channel:**
```python
def unprocessed(tag=None, limit=20):
    q = "SELECT ... WHERE direction='inbound' AND handled_at IS NULL"
    if tag is not None:
        q += " AND tag = %(tag)s"
    q += " ORDER BY id ASC LIMIT %(limit)s"
    # params: {"tag": tag, "limit": limit}

def mark_handled_through(max_id, tag=None):
    q = ("UPDATE operator_messages SET handled_at=now() "
         "WHERE direction='inbound' AND handled_at IS NULL AND id <= %(max_id)s")
    if tag is not None:
        q += " AND tag = %(tag)s"
```
Each consumer only stamps rows it actually processed (or use a per-consumer cursor column). Never stamp across channels a consumer did not answer.

#### [P2] getFile metadata hop has no retry on the flaky Mini↔Telegram path (partial fix)
**Object:** `nervous_system/tg_bridge.py` (mirrored `cai_bridge.py`, `irsyad_support_bridge.py`)
**Location:** `tg_bridge.py:344` & `:358` (getFile) → hands off to retry-guarded `_fetch_telegram_file` (`:312-336`)
**Verdict:** CONFIRMED

The retry+backoff media fix protects only the file-**content** download. The preceding `getFile` metadata call (`urllib.request.urlopen(f"{API}/getFile?file_id=...")`, no retry) hits the *same* `api.telegram.org` host. An Errno-54 reset there propagates to `handle()`'s except (`:380-381`/`:388-389`) and is recorded as `download failed` — still losing the operator's signed DPA / ADCDA screenshot, the exact delivery-bug class the retry was meant to eliminate. Below P1 because the metadata request is short (not the long stream that caused the original incidents) and it fails *visibly* in `operator_messages` (recoverable).

**Fix:** wrap the `getFile` call in the same 4× retry+backoff as `_fetch_telegram_file` (or fold both hops into one retried helper). Apply across all three bridges.

### [1] P1 — RLS misconfiguration (open policy defeats RLS)
**Object/file:** public.jobs, clients, work_outputs, payments, bug_reports, build_log, repo_memory, chat_history, usage_log, pending_signups, message_queue, wingmen_brain, bot_users, bot_conversations, provisions, fleet_lanes, jobs_archive, strategic_decisions_archive (+6 more)

**Summary:** 24 RLS-ENABLED tables are effectively wide-open to anon and authenticated: their SOLE policy is misnamed 'service role full access' but is declared PERMISSIVE FOR ALL TO public USING(true) WITH CHECK(true) — it never checks auth.role(). RLS being ON gives a false sense of protection while granting anon/authenticated full read+write+delete.
**Impact:** Anyone holding the public anon key can SELECT/INSERT/UPDATE/DELETE these tables via PostgREST.
