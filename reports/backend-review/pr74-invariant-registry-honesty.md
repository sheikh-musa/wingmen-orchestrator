## The two things you most wanted attacked — both resolve in the design's favour

**A · Strict "gate_status DOMINATES the timestamp" reading — CORRECT and defensible, not wrong.** A MANUAL assertion is a human who remembered, not a live measurer; §1's own words ("a manual assertion is not a live measurer") mandate the strict reading. PII-ANON-1 reading UNEXERCISED despite its real 2026-07-22 timestamp is the *intended* result: a one-time human assertion 3–4 weeks ago is not continuous measurement, and the lenient alternative would re-admit exactly the "someone remembered" = a-sentence-not-a-control failure. It fails toward UNEXERCISED. This is a cai POLICY call (28-vs-34), correctly escalated to her — the CODE faithfully implements the strict reading you chose. No change; flagging only that it is policy, not code.

**B · Can `is_exercised_fresh` (boolean) and `exercise_state` (label) disagree? — NO. Proven.** Your feared counterexample does not exist.
- Case-exhaustion: `exercise_state='EXERCISED'` ⟺ (live-measurer ∧ non-NULL ts ∧ fresh) ⟺ the `is_exercised_fresh` conjunction, in every branch. The STALE arm (`ts < now()-30d`) and the fresh predicate (`ts >= now()-30d`) are exact complements; `now()` is the statement timestamp (STABLE — one value per query, no skew between the two expressions); and the IN-list holds no NULL, so `NOT IN` never yields UNKNOWN (and NULL gate_status is guarded first).
- **Empirically verified:** replayed both expressions over a 54-cell matrix (gate_status ∈ {NULL, MANUAL, pending, MEASURED, measured, AUTO, AUTOMATED, automatic, LIVE} × last_asserted_at ∈ {NULL, now, −15d, −30d exactly, −30d−1s, −45d}) → **0 disagreements.** They cannot render green off the boolean while the label says UNEXERCISED.

## Findings (LOW–MED; all fail-safe; fix-before-merge is cheap insurance)

**F1 · MED — the 30-day threshold is duplicated, and the duplication is the exact mechanism that could break B.** `interval '30 days'` appears independently in the STALE arm and the `is_exercised_fresh` boolean. They match today (so B holds), but a maintainer tuning the freshness window in ONE place and not the other reintroduces precisely the boolean-vs-label disagreement you were worried about — B's guarantee is only as durable as this coupling. **Single-source it** (one scalar/expression feeding both arms, or derive the boolean from `exercise_state`). The *value* 30d is a fine policy default; the *duplication* is the issue. "Justify or kill" → keep the value, kill the duplication.

**F2 · MED — the apply-script post-condition is load-bearing today but becomes a ROLLBACK LANDMINE once a sink lands.** It asserts `unexercised == total AND fresh == 0`. That is genuinely useful NOW (it would catch a view that lies toward coverage). But it encodes a *transient fact* ("no sink is wired yet"), not the view's *invariant*. The moment the CAI-985 A3 sink legitimately exercises RESIDENCY-1 (`gate_status='MEASURED'` + fresh ts), re-running 047 (a `CREATE OR REPLACE VIEW` that is explicitly designed to be re-runnable) fails the post-condition and **rolls back a TRUE-exercised state — reading correct coverage as a failure.** Re-scope the guard to the actual honesty invariant: assert **no row is `is_exercised_fresh` while `gate_status` is NULL/manual** (the lie this migration prevents), not `count == 0`. Then it keeps catching real regressions after a sink exists instead of becoming a re-apply landmine for whoever wires RESIDENCY-1.

**F3 · LOW–MED — `r.*` + a new base column + re-apply → CREATE OR REPLACE VIEW failure (confirmed empirically).** In a temp table: after `ALTER TABLE … ADD COLUMN`, re-applying the `r.*` view fails with `cannot change name of view column "is_fresh" to "new_col"` — the new base column re-expands into the *middle* of the column list (before the computed columns), and CREATE OR REPLACE VIEW is append-only. So any future `ALTER TABLE invariant_registry ADD COLUMN` silently makes 047 un-re-appliable. **Enumerate the base columns explicitly** instead of `r.*`, so a base-table schema change is a deliberate view edit, not a silent re-apply break.

**F4 · LOW (your allowlist question, answered precisely) — the hardcoded MEASURED/AUTO/AUTOMATED list is NOT a green-lying drift trap; the UNCONSTRAINED `gate_status` free-text column is the real one.** The allowlist fails SAFE: an unrecognised token → UNEXERCISED, never false-green — so unlike the drift traps I flagged in the #60 report, this one can't manufacture coverage. BUT `gate_status` is free text (32 MANUAL + 2 pending, no constraint), so the first sink writing a *variant* token — `AUTOMATIC`, `MEASURD` (typo), `live` — silently reads UNEXERCISED **forever**, looking like broken wiring. You already flagged the write-both-columns coupling to cc-fleet-health (#23684); harden it with a **CHECK constraint / enum on `gate_status`** so a bad sink token fails LOUDLY at write time rather than silently-amber. That closes the drift at the write site, where it belongs.

**F5 · LOW (new, `unexercised_kind` at head 82d9493) — the NEVER / MANUALLY-ATTESTED dichotomy is incomplete, and the case it drops is the most sequencing-urgent one.** When a live measurer is *declared* (`gate_status IN allowlist`) but has *never written* (`last_asserted_at IS NULL`), the row is honestly `exercise_state='UNEXERCISED'` but `unexercised_kind = NULL` ("not an unexercised-kind question") — confirmed 4/54 matrix cells (0 rows today, since no row is yet automated). So a consumer sequencing by `GROUP BY unexercised_kind` over UNEXERCISED rows gets a NULL bucket that is neither NEVER nor MANUALLY-ATTESTED: **a sink declared but producing nothing.** That is exactly the "measurer went silent / never scheduled" class from the #60 report (`bug_pipeline_readiness` frozen because `pipeline_clock` was never scheduled) — the highest-priority thing to surface, here labelled NULL and thus easy to skip. Not a binary defect (`is_exercised_fresh` is false; state is honestly UNEXERCISED). **Recommend:** name it (e.g. `'DECLARED-SILENT'`) or document that sequencing consumers must treat `(exercise_state='UNEXERCISED' AND unexercised_kind IS NULL)` as "declared but never fired," not a no-op. This is when RESIDENCY-1's sink is wired-but-not-yet-writing — the transient you most want visible.
